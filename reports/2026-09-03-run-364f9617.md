## 3. Notebook contamination — RunId reuse

`NOTES.md` lives at `C:\vm-agent\notes\<runId>\NOTES.md` and the run was triggered with `runId = vmagent-001` — **the same value as the 2026-09-02 runs.** The notebook the summarizer read contains two "Pass 1" sections, a Pass 2 and a Pass 3 from yesterday (bucket paths `vmagent-001/…/20260902-21xxxx`), followed by today's "Pass 4". Yesterday's passes were made with the old Slack connector attached (the notebook mentions `search.messages … missing_scope`).

Consequences:

- The flow reports "Investigation passes used: 2 of 6" while the notebook shows 4 passes. Numbers in the final report are wrong.
- The agent's first call read yesterday's notes and *continued* from them ("continuation of Pass 1-3 leg"). In this case that saved work, because it was the same test. Against a different test with the same runId it would have been actively misleading.
- Worth deciding deliberately: either (a) runId must be unique per run (flow should derive it — e.g. `<spec-slug>/<yyyymmdd-HHmm>` — not take it from the trigger), or (b) make cross-night memory a feature keyed by *spec path*, in a separate `MEMORY.md` the agent reads but the summarizer does not count as passes. (b) is the more valuable direction; it is exactly how "less and less over time" would work.

At Anthropic list price (Sonnet 5 $2/$10 per MTok, Opus 4.8 $5/$25 per MTok):

- Investigator: 2.84 M × $2 + 23.4 K × $10 ≈ **$5.92**
- Summarizer: 19.7 K × $5 + 4.25 K × $25 ≈ **$0.21**
- **≈ $6.1 per run in LLM tokens**, plus ~62 min of a Windows cloud robot and ~82 min of one Flow instance.

UiPath bills AI Units rather than USD, so treat $6 as the marginal cost proxy; the AI-unit multiplier on alpha is whatever the tenant is configured with, but the token volume is the thing to shrink either way.

`cacheReadInputTokens: 0` on every call is the headline. If the Agents runtime applied prompt caching (system prompt + tool list + conversation prefix), roughly 90% of that 2.84 M would be cache reads at 10% price: the same run would cost ≈ $0.85 in tokens. Worth asking the Agents team whether `basic-v2` supports caching for Anthropic models; if it does not, that is the single largest cost lever and it is out of the flow's hands.

"Less and less over time" holds only if resolved tests are removed from the input list and unresolved ones carry memory forward (§3b). Without cross-night memory each night restarts from zero and costs the same.

## 5. Improvements, ranked

### Efficiency (do first, cheap)

1. **Install `rg` on the VM image** (`vm-bootstrap.ps1`) and have `setupVm` verify it (`rg --version`) so the prompt's search guidance is true. Removes the two runaway searches — 43 of 69 minutes.
2. **Per-call timeout enforced by the tool, not the prompt.** Pass `TimeoutMinutes` from the flow (e.g. 3) instead of letting the model choose; default `WorkDir`/`RunId`/`TimeoutMinutes` inside the `vm-exec` process so a missing arg never faults the job (fixes call #24).
3. **Cap tool output at ~8 KB in context, keep the 32 KB tail in the bucket** (already uploaded). Context peaked at 189 K tokens mostly from raw file dumps. Add a `MaxOutputChars` input on `vm-exec` defaulting to 8000, and tell the agent to `Select-String` / `Select-Object -First N` instead of `Get-Content` whole files.
4. **Fix prompt drift**: delete the GitHub-tool paragraph and step 3, or replace them with the VM-side path from §6. Delete the "4 calls / 30 min" text or make it true via `maxIterations` on the agent (currently 100; 12–15 fits this task).
5. **Unique runId derived in the flow**, not the trigger (see §3).

### Leading to actual fix proposals (the gap that matters)

The investigator stopped one step short: it knows the failing assertion, the wrong signal, and the right signal (the debounced flow-file PUT/PATCH visible in `0-trace.network`). Everything needed to write the patch is already in context.

6. **Add a `propose fix` phase.** Cheapest version: extend the investigator user prompt — "when the notebook names a cause in the test or page-object layer, make the change in the clone, run only the failing spec (`--retries=0 -g <title>`), and write `git diff` to `C:\vm-agent\notes\<runId>\fix.patch` plus a `## Fix` section (verified / not verified, before/after output)". Expected extra cost: 2–3 `vm_exec` calls, one of them a ~2-minute spec run. Sonnet 5 at 190 K context is already paying for the knowledge; using it is nearly free.
7. **Verify with a positive control** in the same call: run the spec under `--project=standalone` (or whichever host exposes the badge). "Passes elsewhere, fails here" is the strongest possible evidence for the test-helper classification and it costs one call.
8. **Output the patch, not just prose.** `readNotes` should also read `fix.patch`; the summarizer gets a `patch` output field and a `fixVerified` boolean. That is what a human wants in the morning: a diff they can `git apply` and a green/red bit.
9. **Classify before investigating.** A first cheap LLM turn (Haiku 4.5 or Sonnet 5 at low effort) that reads only the test output tail and answers "test-code failure vs product failure vs infra" would have set the right expectations and avoided the GitHub detour. Most nightly e2e failures are the first or third category.

## 6. Slack / GitHub — VM-side only, files not context

The connector-based tools were removed for good reasons (a `search.messages` response or a PR JSON blob is tens of KB straight into context). Doing the same work on the VM and writing to files gives the agent the information at a fraction of the token cost, because the agent controls how much it reads back.

GitHub (higher value):

- Bake `gh` CLI into the VM image; `setupVm` runs `gh auth login --with-token` from the existing `GIT_TOKEN` env var (same secret already used for the clone — no new secret).
- `setupVm` pre-fetches, before the agent starts: `gh run list --branch develop --workflow e2e --limit 20 --json conclusion,createdAt,headSha > C:\vm-agent\ctx\<runId>\ci-history.json` and `gh search issues "<spec basename>" --repo UiPath/flow-workbench --json title,url,state > issues.json`. Deterministic, zero LLM tokens, answers "is this new?" that the prompt currently begs for.
- Agent reads those files with `Select-Object -First 20` when it needs them. Read policy is the agent's, not the connector's.
- Optional, opt-in: after `fix.patch` is verified, a flow decision gate (not the agent) runs `gh pr create --draft` from the VM. Keep it off by default; a `createDraftPr` flow input decides.

Slack (lower value, do second):

- Bot token stays a VM env var (`SLACK_TOKEN`), exposed only through a fixed script in `setupVm`: `Invoke-RestMethod search.messages?query="<first error line>"` → `slack-hits.json`, trimmed to `permalink`, `ts`, `text[:200]`. Needs the `search:read` scope the current bot lacks (that was yesterday's `missing_scope` failure).
- Never let the agent compose Slack calls; one fixed pre-fetch is enough and avoids an agent posting anything.

Either way the shape is the same: **fetch deterministically in `setupVm`, write JSON files, let the agent read what it wants.** Token cost of the whole GitHub context becomes ~2 K instead of ~20 K, and none of it is wasted when the agent does not need it.
